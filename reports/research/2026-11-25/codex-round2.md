### Claude Q1 — stop above market and rejection handling

`ensure_stops()` (`src/tradebot/execution.py:263–292`) rounds the ledger quantity and stop price, then calls `submit()` and `broker.place_stop()`. It obtains no current quote and makes no stop-versus-market comparison. `Engine.sync()` calls this only after reconciliation succeeds and only for broker-open mapped symbols (`live.py:201–225`). `cmd_run()` exits before engine construction while the timed pause is active (`cli.py:155–163`). KILL itself permits protective-stop maintenance.

If submission raises a non-corrected T212Error with status below 500, `submit()` marks the row BROKER_REJECTED and checks the three most recently created attempted ledger orders, across roles/strategies, for consecutive BROKER_REJECTED states (`execution.py:125–140`). Thus **yes, an HTTP-4xx stop rejection counts**. For a newly planned stop, `ensure_stops()` additionally invokes HALT after even one BROKER_REJECTED/NOT_FOUND result. With KILL already set, HALT preserves the original trip and cancels entries; it does not protect the rejected lot. The existing-PENDING-stop retry branch ignores submit's return value, so that branch lacks the same immediate HALT call. A broker response object with status REJECTED, rather than an HTTP exception, follows `_adopt()` and is another distinct path; the HTTP rejection-streak code is not invoked there.

If the broker accepts and immediately fills the stop, `_adopt()` records the returned status/ID but does not apply its fill immediately; normal sync applies it later. Neither outcome should be relied on as the restart policy. Official [stop-order documentation](https://docs.trading212.com/api/orders/placestoporder_1.md) establishes LTP triggering and conversion to a market order; **acceptance versus rejection of an already-breached sell stop is UNVERIFIED** for this account. No test order was sent.

Recursive finding: ordinary planned exits are also blocked by KILL in `execute_pending()`; only an exit with the current flatten reason-prefix exception passes. Consequently P-claude-5 cannot be implemented solely by planning an exit while leaving the rest of execution unchanged. A reviewed recovery-intent design, unresolved-sell reservation and fresh inventory are required; do not repurpose a reason string as authority. This is already within P-codex-2/3/5/6 and the proposed amendment to P-claude-5.

`cancel()` requires a terminal confirmation; `wait_final()` polls the active-order endpoint, and after 404 consults history, for a nominal 60-second timeout (`execution.py:223–253`). `order_history()` searches only the first 50 historical items (`trading212.py:102–109`). Rate-limit waits and request duration happen inside the polling call, so the 60 seconds is not a strict wall-clock bound. When cancel raises, the pending exit has not been submitted; `step()` catches the error and schedules another sync (`live.py:389–399`). That explains the repeated attempts and why the exit waited for cancellation visibility.

**The broker-side root cause is UNVERIFIED.** The ledger does not retain all intermediate GET/DELETE responses, page cursors or rate-limit timings. Delayed final-state visibility, a slow cancellation and history pagination are hypotheses, not diagnosed facts. The recorded error means “no final confirmation observed,” not “the DELETE definitely failed.” The code correctly avoids selling against an unresolved stop; making it sell anyway would introduce oversell risk.

Nor is 07:21:09 necessarily the fill's actual execution time: `apply()` timestamps observation with local now and does not retain the broker fill timestamp. The adverse difference `(56.64−56.44)/56.64 ≈ 0.3531%` is valid **conditional on the report's Yahoo-open value**, but cannot all be causally attributed to cancellation or called measured spread.
